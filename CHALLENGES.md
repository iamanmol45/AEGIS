### [CHALLENGE-001] AWS CDK Python Stack Module Import Resolution Failure

- **Date / Stage**: 2026-09-18 | Infrastructure Initialization & CDK Setup
- **Component**: `infrastructure/app.py` & `infrastructure/infrastructure/infrastructure_stack.py`
- **Severity**: Blocker (Prevented `cdk synth` and `cdk deploy`)

#### 1. Issue Description
When executing `cdk synth` to synthesize the CloudFormation template for the VPC and ECS Cluster, the execution crashed immediately with:
```text
Traceback (most recent call last):
  File "D:\Solo Hackathons\BHARAT BUILDS\AEGIS\infrastructure\app.py", line 5, in <module>
    from infrastructure_stack import InfrastructureStack
ModuleNotFoundError: No module named 'infrastructure_stack'
python app.py: Subprocess exited with error 1
```

#### 2. Root Cause Analysis
- The project generated by CDK placed the stack class inside a subfolder package `infrastructure/` with an `__init__.py` (`infrastructure/infrastructure_stack.py`).
- The root entry point `app.py` attempted a flat module import (`from infrastructure_stack import InfrastructureStack`) rather than referencing the package namespace (`from infrastructure.infrastructure_stack import InfrastructureStack`).

#### 3. Resolution & Fix
- Updated [app.py](file:///d:/Solo%20Hackathons/BHARAT%20BUILDS/AEGIS/infrastructure/app.py#L5) to use the correct Python package import path:
  ```python
  from infrastructure.infrastructure_stack import InfrastructureStack
  ```
- Re-ran `cdk synth` and `cdk deploy`, successfully provisioning the `AegisVpc` and `AegisCluster` (Stack ARN: `arn:aws:cloudformation:ap-south-1:492715479040:stack/AegisInfrastructureStack/24cb0040-b2e3-11f1-87b0-0a72b63311a3`).

#### 4. Key Takeaways
- Always verify CDK's modular directory structure when working with Python templates.
- Ensure the virtual environment (`.venv`) is consistently active when invoking CDK CLI operations.

### [CHALLENGE-002] Docker Build Context Mismatch (Missing Dockerfile in Working Directory)

- **Date / Stage**: 2026-09-18 | Containerization of Monitored API Service
- **Component**: `services/api/Dockerfile` & Docker CLI Build Context
- **Severity**: Low / Operational

#### 1. Issue Description
Running `docker build -t aegis-api .` while inside `AEGIS/services/` resulted in a build failure:
```text
ERROR: failed to build: failed to solve: failed to read dockerfile: open Dockerfile: no such file or directory
```

#### 2. Root Cause Analysis
- The Docker build command defaulted to looking for `Dockerfile` in the current working directory (`AEGIS/services/`).
- The actual service definition and its [Dockerfile](file:///d:/Solo%20Hackathons/BHARAT%20BUILDS/AEGIS/services/api/Dockerfile) reside inside the sub-directory `AEGIS/services/api/`.

#### 3. Resolution & Fix
- Navigate into the service folder or specify the relative context:
  ```powershell
  cd .\api
  docker build -t aegis-api .
  ```
  *Alternative (from `services/`):*
  ```powershell
  docker build -t aegis-api -f .\api\Dockerfile .\api
  ```

#### 4. Key Takeaways
- Ensure docker build context path matches the target microservice folder holding `Dockerfile`, `app.py`, and `requirements.txt`.

### [CHALLENGE-003] Container Runtime Entrypoint Error (`uvicorn: executable file not found in $PATH`)

- **Date / Stage**: 2026-09-18 | Docker Container Local Testing
- **Component**: `services/api/Dockerfile` & Container Execution
- **Severity**: Medium (Container failed to start)

#### 1. Issue Description
When attempting to start the container using `docker run --rm -p 8000:8000 aegis-api`, the container crashed immediately upon instantiation:
```text
docker: Error response from daemon: failed to create task for container: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: exec: "uvicorn": executable file not found in $PATH: unknown
```

#### 2. Root Cause Analysis
- The Docker image was executed prior to rebuilding after navigating into the `api` folder, referencing an outdated or uninstalled state.
- Additionally, invoking `CMD ["uvicorn", ...]` depends directly on binary placement in system `$PATH` inside the container image, which can fail if Python package script binaries are installed in non-standard or user-specific paths.

#### 3. Resolution & Fix
- Updated [Dockerfile](file:///d:/Solo%20Hackathons/BHARAT%20BUILDS/AEGIS/services/api/Dockerfile#L13) to use Python module invocation syntax:
  ```dockerfile
  CMD ["python", "-m", "uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
  ```
- Rebuilt and ran the container from `d:\Solo Hackathons\BHARAT BUILDS\AEGIS\services\api`:
  ```powershell
  docker build -t aegis-api .
  docker run --rm -p 8000:8000 aegis-api
  ```

#### 4. Key Takeaways
- Always rebuild the image (`docker build`) after fixing context or Dockerfile changes before running `docker run`.
- Use `python -m <module>` in `Dockerfile` `CMD` / `ENTRYPOINT` for reliable execution independent of binary `$PATH` lookup quirks.

### [CHALLENGE-004] Empty Requirements File & Docker Build Layer Caching (`No module named uvicorn`)

- **Date / Stage**: 2026-09-18 | Docker Container Dependency Installation
- **Component**: `services/api/requirements.txt` & Docker Cache
- **Severity**: High (Dependencies missing from runtime container)

#### 1. Issue Description
Running `docker run --rm -p 8000:8000 aegis-api` resulted in:
```text
/usr/local/bin/python: No module named uvicorn
```
Even though `docker build -t aegis-api .` completed with exit code 0.

#### 2. Root Cause Analysis
1. [requirements.txt](file:///d:/Solo%20Hackathons/BHARAT%20BUILDS/AEGIS/services/api/requirements.txt) on disk was empty (0 bytes).
2. Because of this, Docker reused the cached step `CACHED [4/5] RUN pip install --no-cache-dir -r requirements.txt`, meaning neither `fastapi` nor `uvicorn` were installed into the image layers.

#### 3. Resolution & Fix
- Populated [requirements.txt](file:///d:/Solo%20Hackathons/BHARAT%20BUILDS/AEGIS/services/api/requirements.txt) with the necessary dependencies:
  ```text
  fastapi>=0.110.0
  uvicorn[standard]>=0.28.0
  ```
- Rebuilt the Docker image and executed the container:
  ```powershell
  docker build -t aegis-api .
  docker run --rm -p 8000:8000 aegis-api
  ```

#### 4. Key Takeaways
- Verify dependency files (`requirements.txt`, `package.json`) are populated and saved on disk before building container images.
- If a build step like `RUN pip install` unexpectedly shows `CACHED` when dependencies are missing, check the source file or run with `docker build --no-cache`.

### [CHALLENGE-005] Empty `app.py` File at Container Image Assembly Time

- **Date / Stage**: 2026-09-18 | Docker Container Runtime Application Loading
- **Component**: `services/api/app.py` & ASGI Initialization
- **Severity**: High (Application failed to boot inside container)

#### 1. Issue Description
Running `docker run --rm -p 8000:8000 aegis-api` failed at startup:
```text
ERROR: Error loading ASGI app. Attribute "app" not found in module "app".
```

#### 2. Root Cause Analysis
- `services/api/app.py` on disk was empty (0 bytes / unsaved buffer) when `COPY app.py .` executed during the Docker image build.

#### 3. Resolution & Fix
- Populated and saved [app.py](file:///d:/Solo%20Hackathons/BHARAT%20BUILDS/AEGIS/services/api/app.py) with the FastAPI endpoints (`/health`, `/api`, and `/stress`):
  ```python
  from fastapi import FastAPI
  import time

  app = FastAPI(title="AEGIS Monitored Service")
  ...
  ```
- Rebuilt and started the container:
  ```powershell
  docker build -t aegis-api .
  docker run --rm -p 8000:8000 aegis-api
  ```

#### 4. Key Takeaways
- Ensure application source files are saved to the file system prior to running `docker build`.

### [CHALLENGE-006] Missing Root Endpoint & Browser Navigation (404 / Unreachable)

- **Date / Stage**: 2026-09-18 | API Service Testing & Endpoint Routing
- **Component**: `services/api/app.py` & HTTP Routing
- **Severity**: Low (UX / Navigation)

#### 1. Issue Description
Accessing `http://localhost:8000` or `http://127.0.0.1:8000` returned a `404 Not Found` / unreachable page perception because no route handler was attached to the root path `/`.

#### 2. Root Cause Analysis
- FastAPI only serves routes explicitly registered. The original implementation had handlers for `/health`, `/api`, and `/stress`, but lacked a root `/` handler. Navigating directly to `http://localhost:8000/` without specifying an endpoint returned `{"detail": "Not Found"}`.

#### 3. Resolution & Fix
- Added a dedicated root handler `@app.get("/")` returning service status, health state, and a sitemap of all available endpoints including FastAPI's built-in interactive `/docs`.
- Rebuilt image and exposed on `http://localhost:8000`.

#### 4. Key Takeaways
- Always provide a descriptive root route `/` and health check route `/health` in microservices to ease local debugging, load balancer health probes, and developer onboarding.

- **Component**: AWS CDK CLI & Directory Context
- **Severity**: Low / Operational

#### 1. Issue Description

#### 2. Root Cause Analysis

  ```powershell

  cdk synth
  ```

#### 4. Key Takeaways
- Always run CDK CLI commands (`cdk synth`, `cdk diff`, `cdk deploy`) from the directory containing `cdk.json`.

### [CHALLENGE-008] ECS Task Role AccessDenied & Stale Service Name on `/status` (500 Internal Server Error)

- **Date / Stage**: 2026-09-19 | Production Deployment & Verification
- **Component**: `services/api/app.py`, `services/api/remediation.py`, `infrastructure/infrastructure_stack.py`
- **Severity**: High (500 Internal Server Error on `/status`)

#### 1. Issue Description
While `/health`, `/policy`, and `/workflow` responded successfully, testing `/status` returned an unhandled HTTP 500 Internal Server Error:
```text
curl.exe "$BASE/status"
Internal Server Error
```

#### 2. Root Cause Analysis
Inspecting the ECS container logs in CloudWatch revealed two cascading failures:
1. **Missing Task Role IAM Permissions**:
   The ECS Task Definition role was created without explicit policies for ECS and CloudWatch. Calling `ecs.describe_services()` raised `botocore.errorfactory.AccessDeniedException: ... is not authorized to perform: ecs:DescribeServices`.
2. **Stale Hardcoded Service Name**:
   The code had the ECS service name hardcoded to `AegisInfrastructureStack-AegisApiServiceCEE6438E-NeHqjB9uxdtT`, whereas the active ECS service in the cluster had regenerated to `...-3UL7oJqplNbq`. This would also cause an unhandled `IndexError` on `["services"][0]`.
3. **No Defensive Fallback**:
   `/status` lacked `try/except` guards around dynamic metric and cluster inspection calls.

#### 3. Resolution & Fix
1. Attached an inline IAM policy to the ECS Task Role granting `ecs:DescribeServices`, `ecs:UpdateService`, `ecs:ListServices`, `cloudwatch:GetMetric*`, and `states:*`. Updated [infrastructure_stack.py](file:///c:/Users/pranj/AEGIS/infrastructure/infrastructure/infrastructure_stack.py) so CDK retains these permissions.
2. Implemented dynamic service discovery in [remediation.py](file:///c:/Users/pranj/AEGIS/services/api/remediation.py), [recovery.py](file:///c:/Users/pranj/AEGIS/services/api/recovery.py), and [controller.py](file:///c:/Users/pranj/AEGIS/services/api/controller.py) using `list_services()`.
3. Added defensive error handling in [app.py](file:///c:/Users/pranj/AEGIS/services/api/app.py) `get_system_status()`.
4. Built and pushed a new container image to ECR and triggered an ECS rolling update.

#### 4. Key Takeaways
- Container tasks communicating with AWS control planes require explicit IAM Task Role permissions.
- Never hardcode CloudFormation resource suffixes that can drift across stack deployments; use dynamic resource discovery or environment variable injection.
